# PaperPath 能力深挖与技术壁垒路线

日期：2026-09-10。

本轮是产品与技术方向分析，依据当前工作区代码和上一轮模拟器实拍。
没有修改业务代码，没有运行测试套件，没有据旧文档推断当前竞品能力。
下文“已有”指代码中存在实现，不代表复杂样本、真机或长期运行已经验收。

后续实施状态（同日）：已修正脱敏先烧入位图再编码的顺序，并完成 Word 字段边界、
续行和原页参考图改进；实际中英文样本的 DOCX / XLSX / PPTX 已生成并复核。
共享结构模型、结构人工纠正和处理意图校验仍属于后续路线，不能由这些局部改进
推导为已完成。脱敏产物内部图像提取检查尚未完成验收。
详见[第 93 节](COMPETITIVE_BENCHMARK_2026_ZH.md#93-体验缺口补齐与运行阻塞修复)；
下文保留分析时点的事实与设计，不作为最新实现状态清单。

## 1. 核心判断

PaperPath 已经超出“PDFKit 阅读器加几个按钮”的阶段，但还不能把功能数量、
检查项数量和自研代码规模等同于技术壁垒。

最有价值的定位仍是：**在本机完成专业文档处理，让用户知道改了什么、保留了什么、
发出去的具体是哪一版。** 合同、票据、表单和交付材料比泛化的“所有 PDF 用户”
更适合作为近期深挖范围。

建议集中三条主线：

1. 理解文档结构，而不只提取一串文字。
2. 验证处理意图，而不只验证文件能打开。
3. 用 iPad 工作台把复杂处理变成可定位、可纠正、可继续的工作。

## 2. 现有能力与实际边界

| 领域 | 当前实现 | 真正值得补的深度 |
| --- | --- | --- |
| Word 导出 | 文字行、字号、粗体、间距推断段落及简单表格 | 阅读顺序、混排样式、独立字段、跨页结构、可纠正的版面模型 |
| Excel 导出 | 逐页建工作表，逐行按文字间隙切列 | 空单元格、跨行单元格、合并格、跨页续表及有类型的数值 |
| OCR | 本地 Vision、重试增强、文字块坐标、置信度、用户纠正、双栏启发式 | 将位置和纠正信息共享给导出、实体、比较；按页恢复 |
| 文档理解 | 英文关键词分类，NSDataDetector 和正则提取实体 | 字段角色、业务一致性、多语言、可靠来源与拒绝猜测 |
| 版本比较 | 页面配对、重复模板锚点、字符细化、矢量定位、可视证据、签名报告 | 跨页段落搬移、排版噪声抑制、关键金额/日期/措辞变化 |
| 可信交付 | 重开、渲染、空白页、文字层、批注、元数据、修订绑定、指纹 | 按具体处理计划验证“该改的改了，不该改的没动” |
| 任务执行 | 文档互斥、原子事务、恢复日志、Office 队列、温度/空间控制 | 跨任务资源预算、按页中间产物、局部复用及统一状态管理 |

这些领域已有大量实现，下一轮不应再重复“新增 OCR / 差异比较 / 队列 / Receipt”。

## 3. P0：先处理脱敏的底图残留风险

### 静态确认的事实

- [PDFOutputService.swift](../PaperPath/Services/PDFOutputService.swift#L4796-L4833)
  先将完整页面缩略图编码为 JPEG 并绘入 PDF，再在 PDF 上填充黑色矩形。
- [createRedactedCopy](../PaperPath/App/PaperPathModel.swift#L8083-L8102)
  使用上述路径。
- [createOutputCopy](../PaperPath/App/PaperPathModel.swift#L15585-L15646)
  随后执行审计并导入该产物，所查路径中没有把合成后的页面再烧入新的位图。
- [文字层检查](../PaperPath/Services/PDFDeliveryAuditService.swift#L1358-L1370)
  以可提取文字数量为零判断文字层删除，不能证明图像像素里的内容被删除。

### 风险判断

这是高置信的静态安全风险：PDF 中的图像绘制和黑块绘制是不同操作，外观遮挡
不等于底层图像被改写，接收者可能通过提取图像对象恢复被遮住的信息。
本轮没有从 App 的实际脱敏产物中执行图像提取，因此不把它写成已完成利用复现。
但在修复和产物级确认前，不应依赖当前“永久脱敏”处理真实敏感资料。

### 首批修复设计

1. 在内存位图上烧入不透明遮罩，然后编码处理后的像素；不得先把未遮挡图像写入输出 PDF。
2. 明确 PDF 页坐标、CropBox、旋转和图像像素坐标的变换，覆盖部分区域与页边缘。
3. 输出使用全新文件，不携带原图、原文字层、增量历史或原始附件。
4. 从输出对象检查图片和文字，而不只看渲染截图；必要时对烧入后的图像做本地 OCR 辅助复核。
5. 区分“用户标记的区域已处理”与“全篇所有敏感信息都已发现”，后者不能靠前者推导。

OCR 没有识别到敏感词只是辅助证据，不是不可恢复证明。
这首先是产品承诺必须满足的安全底线，不应包装成可选的高级功能。

## 4. P1：共享的文档结构模型

### 当前瓶颈

- [IndexedPageText](../PaperPath/Services/DocumentUnderstandingService.swift#L49-L85)
  主要保存页码和纯文本。
- [OCR 转文字索引](../PaperPath/Services/DocumentUnderstandingService.swift#L356-L388)
  没有把文字块的几何与置信度带入此索引；完整 OCR 结果另有保存，不是原始坐标已丢失。
- [DOCX 段落合并](../PaperPath/Services/DOCXExportService.swift#L1326-L1448)
  依赖行距、字号、缩进等规则，并将同段内的文字行用空格连接。
- [XLSX 行列提取](../PaperPath/Services/DOCXExportService.swift#L2475-L2584)
  另做了一套按行、按文字间隙分列的逻辑。

上一轮发票在 Word 中合并成连续段落，与这类处理方式相符。
真正难点不是生成 OOXML，而是从缺少语义的 PDF 恢复可靠结构。

### 最小可用模型

先在现有解析结果上建立一个有边界的中间表示，不从头实现 PDF 文件解析器：

```text
文档修订 -> 页面 -> 区块 -> 文字行/样式片段
                        -> 表格/行/单元格
                        -> 图片/表单控件

每个节点：
来源类型、原页坐标、稳定定位依据、原始文本、推断角色、
置信等级、人工纠正状态、分析器版本、是否完整
```

原生文字与 OCR 通过适配器进入同一模型；几何、阅读顺序和业务角色分别推断。
不要用每次重新解析生成的随机 UUID 冒充跨修订稳定身份。
先保证同修订内的节点可重定位，再用上下文匹配建立显式跨修订映射。

### 用户能感受到的第一批能力

- 发票的编号、收款人、日期、金额各自保留，不被合并为一段。
- 双栏合同按正确顺序导出，页眉页脚不混入正文。
- Excel 空列不左移，账号与编号保留前导零，金额使用明确地区格式。
- 用户圈选表格、调整一条列边界，立即更新预览；不必重新转换整份文件。
- 来源 PDF 和转换结构之间可以点选联动，纠正结果供后续导出复用。

先从独立字段、段落和规则表格切入，再增加跨页续表、合并格和复杂浮动对象。
读取顺序准确率、字段保留率、单元格定位和人工纠正次数，比“导出成功率”更有意义。

## 5. P1：从通用审计升级为处理意图校验

### 当前边界

[changeReviewCheck](../PaperPath/Services/PDFDeliveryAuditService.swift#L3901-L3964)
主要按操作种类判断可视变化是否符合预期；对于编辑、脱敏等，变化本身被视为合理。
这不等于知道用户只允许改第几页的哪块内容。

### 增量设计

每次操作产生一个明确、不可随页面状态悄悄改变的处理计划：

- 输入修订和页映射。
- 允许变化的区域、字段或结构。
- 必须保留的文字、页面、批注、附件等约束。
- 必须删除的内容与输出策略。
- 实际采用的解析能力、检查覆盖范围及未检查项。

写入器执行计划，校验器重新读取最终产物检查计划；校验结果不能只复述写入器的统计。
签名只能改变指定签名区域，脱敏只能改变标记区域及明确批准的结构，
压缩需要检查文字和细线质量，而不是只检查字节变小、页面数相同。

现有审计使用有界分辨率和片段预算，适合快速定位变化，但不是完整外观等价证明。
可先粗筛，再针对风险页和意图边界做更高分辨率检查，超预算则显示检查不完整。

Receipt 应区分：文件身份、结构检查、内容保留、人工确认。哈希证明字节身份，
签名证明对应密钥的签署，二者都不独自证明内容正确、签署者法律身份或时间真实性。

### 更长期的高保真安全输出

当前 [safeShare/flatten/compress](../PaperPath/Services/PDFOutputService.swift#L1686-L1750)
走整页栅格化。可探索“已净化位图输出”与“结构保留输出”两条不同合同：
前者优先清除底层内容，后者保留清晰文字、链接及可访问性，但需要严格结构白名单。
未经证实可安全处理的 PDF 应回退或拒绝，不应把保留原页面对象误当安全净化。

## 6. P1：有业务含义的版本审阅

不再新增一个比较按钮，而是在现有字符和矢量差异上回答“什么重要内容变了”。

已有 [字符差异细化](../PaperPath/Services/PDFDeliveryAuditService.swift#L3233-L3517)
和 [比较工作区](../PaperPath/Views/DocumentInsightView.swift#L4207-L4260)。
当前片段配对仍受局部位置与页配对约束，段落搬移和重新分页值得进一步处理。

优先支持：

- “金额从 1,280 改为 12,800”“截止日期提前”“收款账号发生变化”。
- 将纯字体、位置、分页变化与内容变化分开。
- 识别段落搬移，而不把同段内容重复显示为删除和新增。
- 每条差异绑定两侧修订及证据位置；正文再次变化后，旧审阅状态不得沿用。
- iPad 显示原稿、修订稿、差异清单，按项目逐条确认；窄屏改为同一差异的前后切换。

先做确定性金额、日期、账号和否定词变化，再研究更复杂的语义解释。
系统不能把“可能影响责任的措辞变化”直接判断为法律风险，更不能替用户自动接受。

## 7. P2：面向票据和表单的本地字段工作流

当前 [文档理解](../PaperPath/Services/DocumentUnderstandingService.swift#L433-L640)
主要是英文关键词分类、系统检测器和正则；分类置信度来自命中数。
[DetectedEntity](../PaperPath/Models/DocumentModels.swift#L10113-L10196)
具有类型、值和页码，但尚不是包含字段角色、精确区域与推断证据的业务数据模型。

可从“发现了四个金额”升级到：

- 区分小计、税额、应付金额；以 Decimal 和显式币种做一致性检查，不擅自换算。
- 保留原始字符串及规范值；日期有歧义时要求确认，不自动猜月日顺序。
- 对同一供应商的票据记住用户确认过的字段位置与标签。
- 利用标题、标签和相对几何匹配模板，模板不匹配时拒绝静默套用。
- 多份文件汇总到账目表，每个单元格可返回原文证据。
- 在已有表单填写能力上提供确认后的字段映射，而不是默认从任意文件读取并填入敏感资料。

本地小模型可以是未来的区块分类或字段候选适配器，不应该先做泛聊天入口。
模型只提出候选，确定性校验器确认来源与类型；低置信度不能自动落盘。
需要评估离线可用性、设备/系统版本、语言、包体、延迟与低内存回退；
不能让 iOS 17 基础流程依赖某个新系统专属模型。

## 8. P1/P2：可恢复任务与模块边界

### 已有基础，不重新造轮子

- [DocumentStore](../PaperPath/Services/DocumentStore.swift#L8412-L8469) 已有事务恢复。
- [Office 资源控制](../PaperPath/App/PaperPathModel.swift#L3650-L3700) 已看温度、空间、低电量。
- [批量预检](../PaperPath/App/PaperPathModel.swift#L9229-L9337) 已有限并发和修订缓存。

### 真实增量

当前 [OCR](../PaperPath/Services/VisionOCRService.swift#L26-L109) 汇集页面结果后返回，
[上层](../PaperPath/App/PaperPathModel.swift#L7406-L7504) 再保存分析。
可以增加与最终文档隔离的页级中间结果，使中断后不必把已识别页全部重算。

缓存键必须包含源修订、页面身份、参数、算法版本；旋转、裁切及文字变化不能误复用。
全 App 共享有界资源预算，协调 OCR、转换、差异、缩略图，而不只各自限流。
前台翻页优先，后台分析让步；iOS 挂起时保存已完成阶段，不承诺任意后台永久运行。

当前 `LibraryView.swift` 约 2.68 万行，`PaperPathModel.swift` 约 1.74 万行。
这些数字不是崩溃原因的证明，但已说明职责集中程度较高。
按资料库、Office、交付、比较提取功能状态与控制器，保留已有存储原子提交边界。
新能力应接入明确模块，而不是持续堆入同一个页面和主模型。

`Task.detached`、actor、`do/catch` 不提供进程隔离，也不能兜住所有 UIKit/PDFKit
断言或 SIGABRT。iOS 不能按桌面程序的方式任意拉起解析子进程来承诺“永不崩溃”。

## 9. 优先级与执行顺序

| 顺序 | 切入点 | 用户收益 | 技术价值 / 风险 |
| --- | --- | --- | --- |
| 0 | 脱敏先烧入位图，再核对输出对象 | 防止“看不见但仍可取出”的泄露 | 安全必需；坐标和编码顺序需严谨 |
| 1 | 共享结构模型最小版 + 发票字段/段落 | 直接改善已经实拍暴露的 Word 问题 | 高复用；控制首批支持范围 |
| 2 | 表格区域选择、列纠正、字段类型 | Excel 从“能生成”变成“能用” | 高价值；交互纠错降低自动识别要求 |
| 3 | 处理计划 + 限定区域的产物校验 | 更可靠地解释交付结果 | 与现有审计协同；禁止不完整检查冒充通过 |
| 4 | 关键字段差异 + iPad 审阅任务 | 把已有比较深度变成工作效率 | 差异化强；依赖可靠定位和字段结构 |
| 5 | 页级恢复、资源预算、功能模块拆分 | 长文档中断后能继续，前台少被后台拖慢 | 是持续迭代基础；不改坏提交语义 |
| 6 | 本地模板和跨文档字段核对 | 重复处理票据、表单更省操作 | 用用户确认样本收敛；不默认收集隐私数据 |

不建议先投：更多低频格式、泛 AI 聊天、自研完整 PDF 解释器、云协作、
任意复杂 PDF 原文重排，以及继续增加不能量化含义的“置信分数”。
如未来必须支持复杂结构保留/原文编辑，应单独评估成熟引擎的许可、离线处理、
包体和费用，不默认引入，也不靠无限增加局部规则承诺通用能力。

## 10. 如何形成壁垒，而不是增加工程量

壁垒不是上述算法名本身。真正可积累的是：特定文档类别的高质量结构恢复、
人工纠正经验、明确的失败边界和稳定的完整工作流。当前没有市场数据证明壁垒已形成。

现阶段可按用户要求继续用模拟器和实际产物验证，而不是先建大型自动化体系：

- 准备合法可用的合成或脱敏样本，覆盖发票、合同、表单的少数高频结构。
- 保留原稿、结果、预期结构和人工纠正记录，不只保存一张成功截图。
- 记录正确保留的关键字段、表格位置、误报差异及完成任务需要的修正次数。
- 对“没有查完”“不能可靠识别”给出明确状态，不用推测结果补空缺。

最值得先做的一段闭环：
**安全脱敏底线 -> 票据结构恢复 -> iPad 原稿/结构联动纠正 -> 高质量导出 ->
按处理意图复核。** 这比一次铺开更多独立功能更能提高产品上限。
