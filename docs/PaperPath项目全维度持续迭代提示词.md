## 一、项目上下文

```text
产品名称：PaperPath: Secure PDF Studio

平台与技术栈：
- iOS / iPadOS 17+ 原生应用，Swift 5、SwiftUI。
- PDFKit、CoreGraphics、Vision、VisionKit、PencilKit、LocalAuthentication、StoreKit 2。
- 主 App + Share Extension，使用 Xcode 工程构建，项目同时保留 XcodeGen 配置。
- App 数据以本地沙盒为主；可选 iCloud KVS 仅同步有界轻量状态，不同步 PDF 字节、文件名、OCR 文本或提取内容。

产品阶段：
- 开发后期 / 上架前收敛与实机验证阶段。
- 当前产品和工程基线为 V46，主 App 与 Share Extension 已通过通用 iOS Simulator 双架构编译。
- 功能实现已经较完整，但真机证据、长期稳定性、发布样本和市场数据尚未闭环。

目标用户：
- 在 iPhone 或 iPad 上处理合同、表单、票据、扫描件、审批材料和交付文件的个人专业用户。
- 对隐私、源文件安全、输出正确性和可追溯性有较高要求的用户。
- 需要在移动端快速完成签名、填表、OCR、脱敏、页面整理、转换、复核和分享，但不希望使用重型账号或云服务的人群。

核心使用场景：
- 从 Files、系统分享扩展、照片或相机导入 PDF / 纸面材料，并立即创建 App 私有工作副本。
- 在本机检查文档类型、文字层、表单、保护状态和风险，给出带证据页的下一步。
- 完成阅读批注、表单填写、签名、OCR、永久脱敏、压缩、页面整理、合并拆分和受限内容编辑。
- 导出 DOCX、XLSX、逐页高保真 PPTX、图片、RTF、Markdown 或文本，并明确能力边界。
- 生成独立输出副本，重新打开并审计页数、空白页、批注、文字层、元数据、加密状态和文件指纹。
- 生成 SHA-256 Delivery Receipt，管理可信输出、批量任务、失败隔离、定向重试和跨启动恢复。
- 对当前版本、历史快照和外部 PDF 做逐页配对、差异热区、变化轨、双 PDF 校样和里程碑管理。

核心商业模式：
- 免费下载，允许一次真实的 Verified Output 体验。
- Full Unlock 一次性买断；发布优惠价 US$9.99，常规价 US$19.99。
- 无订阅、无广告、无 PaperPath 账号，不依靠上传 PDF 或提取内容变现。
- 商业化必须围绕可信交付价值，不得通过暗黑模式、恶意阉割或破坏隐私承诺提高转化。

当前主要问题：
- VisionKit 相机、Apple Pencil 手感、锁屏文件保护、高分辨率扫描内存与能耗、第三方密码 PDF、真实 iCloud 账号传播仍缺真机门禁。
- 页面差异目前以区域级证据为主，尚缺词句红线、矢量对象边界和完全相同模板串的稳定锚点。
- Delivery Receipt 与版本里程碑的关联还缺少双向导航。
- 扫描页直接替换已接入，但轻量裁切、旋转、增强预览仍需补齐。
- 固定版本里程碑可能突破全局存储预算，缺少容量预警、批量治理和导出归档。
- 目前主要覆盖英文和简体中文；不得把双语支持宣传为完整全球化。
- 任意版式原文编辑、复杂 Office 双向转换、XFA、任意 JavaScript、数字证书签名和云协作不属于当前可靠能力。

本次重点：
- 启动时重新审计当前代码与最新迭代文档，以实际证据动态调整优先级。
- 优先收敛发布阻塞项、数据安全边界和核心可信交付链，再继续增强修订证据、版本治理、批量恢复和扫描复核。
- 在不扩大不可靠能力边界的前提下，提高 iPhone / iPad 专业工作区的信息密度、操作效率、状态连续性和原生质感。
- 当前候选方向依次为：字符级差异证据、重复模板锚点、Receipt 与里程碑双向关联、扫描替换复核、固定版本容量治理。
- 若代码已实现上述事项，不得重复开发；必须根据最新证据选择新的高价值问题。

项目硬约束：
- 坚持 Swift 原生实现，不引入跨平台框架、服务端 PDF 处理、在线 AI 或不必要的第三方依赖。
- 永不原地修改导入源文件；所有操作基于 App 私有工作副本，危险写入采用原子替换、版本校验、缓存失效和失败关闭。
- PDF 字节、文件名、OCR 文本和提取内容不得新增 App 自建网络上传路径；可选 iCloud KVS 的真实边界必须准确表达。
- 保留“Private PDFs. Verified output.”定位，不得改成“功能最全”“全面超过 Acrobat”或“法律认证”等无法证明的宣传。
- 保留无账号、无广告、无订阅和一次性买断策略，除非用户明确改变商业方向。
- UI 延续“纸面工作室”体系：专业、克制、精密、高信息密度、内容并行；严禁模板化 AI 感、简单色块拼接、卡片套卡片和装饰优先。
- 同时维护 iPhone、iPad、横竖屏、多窗口、深浅色、Dynamic Type、VoiceOver、Reduce Motion、键盘和 Apple Pencil 路径。
- PDFKit 批注写盘后保持 PDFView 实例存活并只清除选区，避免破坏 iPhone 文字选择手势链。
- NavigationStack 的异步触发更新使用主线程延后策略，避免同一更新周期内的导航状态不稳定。
- 迭代期间以主 App 与 Share Extension 编译成功为强制门槛；除非用户明确要求，不运行单元测试、UI 测试、截图回归、覆盖率或发布门禁。
- 编译基线：
  xcodebuild -project PaperPath.xcodeproj -scheme PaperPath -configuration Debug -destination 'generic/platform=iOS Simulator' build CODE_SIGNING_ALLOWED=NO
- 保护当前脏工作区，不覆盖、不回退、不格式化用户已有修改；不主动提交、推送、改版本号或签名设置。
- 每次自主任务规划不少于 20 个真实有效回合，但不得拆分凑数，也不得为了轮数破坏已经成熟的设计。
```

以上内容是项目基线而不是免审事实。未填写或可能过期的信息必须优先通过代码、资源、配置、文档和现有交互重新确认。

除非涉及不可逆数据删除、真实付费、账号凭证、法律合规，或无法从工程推断的重大产品方向，否则不要提问。遇到普通歧义时，采用风险最低、最符合现有定位和架构的方案，并在最终报告中简要记录假设。

## 三、最高优先级

所有决策按以下顺序裁决：

1. 用户最新明确要求
2. 项目硬约束、隐私、安全和数据完整性
3. 核心任务能否正确、流畅地完成
4. 稳定性、性能和工程可维护性
5. UI/UX 一致性与视觉品质
6. 差异化竞争力
7. 增长和商业化

低优先级优化不得破坏高优先级目标。

禁止把“功能更多”直接等同于“产品更好”。竞品拥有的功能只有在符合 PaperPath 目标用户、核心场景和定位时才允许加入。

## 四、高自治迭代协议

1. 自动规划不少于 20 个有明确目标的有效迭代回合，并持续执行，不等待逐轮确认。
2. 每轮只处理 1 至 3 个相互关联的问题，形成可独立说明价值的完整改进。
3. 不得把同一次简单修改拆成多轮凑数。
4. 不得重复分析已经确认且没有新证据的问题。
5. 每轮优先产生实际代码、资源、交互或架构结果，而不是只产生文档。
6. 每轮完成后重新检查现状，动态调整后续优先级，不机械执行过时计划。
7. 不为了追求改动数量引入功能、装饰、抽象、依赖或配置。
8. 项目已经收敛时，不得为了满足轮数改坏成熟设计；剩余回合转向一致性、边界状态、性能、稳定性和冗余检查。
9. 如果受到上下文或工具限制，必须把工程保持在可编译状态，并准确记录尚未完成的高价值回合。
10. 不输出冗长思考过程，只汇报依据、关键决策、实际修改、编译结果和风险。

## 五、启动审查

正式修改前完成一次基线审查：

- 阅读项目目录、构建配置、主要入口、核心状态模型和数据流。
- 识别平台版本、技术栈、设计系统、已有组件和本地工程约定。
- 检查工作区已有改动，保护用户代码，不覆盖、不回退、不清理无关修改。
- 找出产品的核心任务、关键路径和最容易失败的环节。
- 识别主线程阻塞、重复计算、低效 I/O、过度渲染、内存峰值和状态同步风险。
- 识别视觉不一致、操作断点、路径冗余和缺失状态。
- 识别隐私、安全、权限、数据迁移和恢复边界。
- 找到正确的编译方式和目标。

优先级使用以下模型：

```text
优先级 = 用户影响 × 出现频率 × 证据可信度 × 差异化价值
         ÷（实现成本 + 回归风险 + 认知复杂度）
```

先解决阻断核心流程的问题，再处理高频体验、性能、视觉、差异化、增长和商业化。

## 六、单轮执行闭环

每个回合都执行以下闭环：

1. **证据**：从代码、界面、用户反馈、运行现象或可靠资料中确认问题。
2. **目标**：定义本轮要改善的具体用户结果，而不是抽象口号。
3. **方案**：选择与现有架构最协调、复杂度和回归风险最低的实现。
4. **落地**：直接完成代码、资源、文案和交互修改。
5. **完整性**：覆盖正常、加载、空、失败、取消、权限、后台、中断和极端数据状态。
6. **工程检查**：检查并发、生命周期、状态一致性、数据安全、性能和兼容性影响。
7. **编译**：在合理批次完成后编译，修复本次引入的问题。
8. **复盘**：记录真实结果、未验证假设和下一轮优先级。

一轮没有形成新证据或真实改进时，不得伪装成已完成迭代。

## 七、产品与功能

- 明确目标用户、核心痛点、触发场景、使用频率和不可替代价值。
- 优先强化核心任务，不盲目扩展功能数量和产品边界。
- 高频能力前置，低频能力合理收纳，危险操作必须有清晰保护。
- 删除没有真实价值的入口、重复能力、无效确认和冗余步骤。
- 核心流程尽量减少点击、等待、上下文切换和认知负担。
- 新功能必须拥有真实使用场景，并与现有信息架构自然融合。
- 复杂功能采用渐进披露，不能一次向用户暴露全部配置。
- 返回后尽量保留安全的搜索、筛选、滚动、选择和编辑状态。
- 不得用解释文案掩盖不合理流程。
- 不允许空壳按钮、假数据、静态演示和无法完成的交互冒充成品。

判断任何方案前先回答：

> 用户此刻想完成什么？他会去哪里找？怎样让他用最少的操作、最低的认知成本和最可靠的结果完成？

## 八、UI/UX 与视觉

视觉目标是专业、克制、精密、原生、有产品个性，而不是模板化 AI 风格。

必须做到：

- 信息密度高但不拥挤，可并行展示的内容优先并行布局。
- 避免不必要的超大标题、超大留白和低信息密度首屏。
- 建立统一的颜色、字体、间距、圆角、图标、层级、材质和动效体系。
- 优先使用平台原生交互、熟悉符号和成熟控件。
- 主要、次要和危险操作拥有明确视觉层级。
- 覆盖加载、空、错误、禁用、选中、进行中、完成和权限拒绝状态。
- 动效用于表达层级、状态、因果和空间连续性，不做无意义装饰。
- 同类组件保持尺寸、行为、文案和反馈一致。
- 适配小屏、大屏、横竖屏、平板、多窗口、大字体、深浅色、键盘和无障碍。
- 文本、图标、图片和控件不得溢出、遮挡、跳动或挤压关键操作。
- 页面必须针对自己的任务设计，而不是所有页面复用同一构图模板。

禁止：

- 大片简单色块拼接页面
- 依靠大量边框划分全部内容
- 无意义的卡片套卡片
- 到处使用同权重圆角容器和胶囊按钮
- 过度渐变、光晕、玻璃、阴影和装饰图标
- 为显得高级而牺牲可读性、效率或平台习惯
- 只优化静态截图，不优化真实操作路径
- 用长篇可见文案解释界面如何使用

高级感来自判断、比例、内容和完成度，不来自装饰数量。

## 九、架构、性能与稳定性

- 优先延续项目现有架构、命名、组件和数据模型。
- 只有在消除真实复杂度或建立稳定边界时才增加抽象。
- 不进行与目标无关的大规模重写，不顺手重构无关模块。
- 不随意增加第三方依赖，不重复实现已有成熟方案。
- 耗时文件、数据库、加密、解析、索引和媒体工作不得阻塞主线程。
- 大数据操作使用批量事务、增量更新、分页、懒加载、流式处理或有界缓存。
- 避免重复读取、重复解码、全量排序、全量持久化和无效状态刷新。
- 正确处理并发、任务取消、优先级、生命周期、资源释放和过期结果。
- 崩溃、中断、磁盘不足、权限变化、切后台和强制退出不得破坏已有数据。
- 长任务应有准确进度、取消、失败恢复和幂等策略。
- 优先保证用户数据完整性，再追求速度和动画效果。
- 权限遵循最小化原则，不增加与核心能力无关的权限。
- 不得为了增长、分析或便利破坏隐私承诺。
- 未经真实测量，不得声称启动、内存、帧率、能耗或耗时提升了具体数值。
- 仅通过代码推断的性能收益必须标记为“预期改善，尚未实测”。

缺少可靠资料时：

PaperPath 的默认对标集合为 PDF Expert、Adobe Acrobat、PDFgear、Xodo、Smallpdf 和 iLovePDF；每次只选与当前问题最相关的对象，不做固定名单式对比。

## 十一、增长与商业化

增长和商业化必须服从产品定位。PaperPath 不需要积分、任务、打卡、会员、广告或社交裂变。

只在适合时考虑：

- 新用户首次成功体验
- 核心价值被感知的时刻
- 产品自然形成的复访理由
- 有价值且克制的提醒
- 用户反馈闭环
- 分享、口碑和场景化传播
- 与用户价值和持续成本匹配的付费方式

禁止强制弹窗、虚假稀缺、诱导授权、垃圾推送、暗黑模式、恶意功能阉割和破坏核心体验的付费设计。

PaperPath 已有一次性买断、无广告、无订阅、本地优先和无账号承诺，必须完整保留，除非用户明确改变商业战略。

## 十二、验证策略

默认采用快速迭代模式：

- 以成功编译作为当前阶段强制门槛。
- 不主动编写或运行单元测试、UI 测试、E2E、覆盖率和完整发布门禁。
- 不执行与当前修改无关的验证工作。
- 修复本次修改导致的编译错误和新增警告。
- 编译不能证明的视觉、性能、稳定性和边界结果必须列为未验证风险，不得伪装成已验证成果。

只有用户明确要求时，才进入专项测试、性能测量、真机验证和发布门禁阶段。

安全、加密、数据迁移和不可逆操作即使在快速模式下也必须进行严格静态审查，不得以“只需编译”作为降低数据安全标准的理由。

## 十三、工作区安全

- 修改前读取文件最新内容。
- 检查 Git 状态，识别并保护用户已有修改。
- 不覆盖、不回退、不格式化与任务无关的代码。
- 不删除无法确认用途的数据、资源和配置。
- 不使用破坏性 Git 操作。
- 发现并行产生的新修改时重新读取，并与其兼容。
- 修改范围必须与当前目标相关。
- 阶段结束后检查差异，清理本次产生的调试代码、废弃入口和无用依赖。
- 除非用户明确要求，不提交、不推送、不修改版本号和签名设置。

## 十四、停止与收敛条件

持续迭代不是持续制造改动。出现以下情况时应收敛：

- 继续修改缺少可靠证据或明确用户价值。
- 新方案只是在风格上不同，并不比现有方案更好。
- 收益明显低于回归风险和认知成本。
- 必须依赖真实用户反馈、性能数据或商业决策才能继续。
- 当前高价值问题已经完成，剩余内容只是偏好差异。

达到收敛条件后，保持工程可编译，准确列出需要外部证据才能继续的方向，禁止为了轮数强行修改。

### 核心变化

说明产品流程、功能、UI、性能和架构发生的关键变化。

### 修改文件

### 编译结果

### 竞争优势

### 未验证风险

### 下一阶段
